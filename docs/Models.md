# Models

A model is three Darknet files:

| File | Content |
|---|---|
| `.cfg` | Architecture: input size, layers, anchors, classes |
| `.names` | Class labels, one per line |
| `.weights` | Parameters |

`NetworkDescription` builds the `NetworkSpec` from the `.cfg` and `.names`.
`DarknetWeightSource` reads the `.weights` and folds batch-norm into the convolution weights
and biases. Both work with any `Stream`. For creating a model, see [Training](Training.md).

## Loading a model

Use `TinyYoloModel` with a model source. The model can come from flash or from the SD card.

From flash, the three files are converted to `PROGMEM` arrays with `tools/bin2header.py`:

```bash
python3 tools/bin2header.py DarknetModel.h \
    kModelCfg=model.cfg kModelNames=model.names kModelWeights=model.weights
```

```cpp
#include <TinyYolo.h>
#include "DarknetModel.h"
FlashModelSource source(kModelCfg, kModelNames, kModelWeights);
TinyYoloModel model;
model.begin(source);
```

From the SD card, the files are `/model.cfg`, `/model.names` and `/model.weights`:

```cpp
#include <TinyYolo.h>
#include <TinyYolo/app/SdModelSource.h>
SdModelSource source("/model", SS);     // base path, chip-select pin
TinyYoloModel model;
model.begin(source);
```

The model source is read during `begin()`. The `NetworkDescription` and the weights are
kept inside `TinyYoloModel`, so no other object needs to outlive it.

To build the description and weights by hand, use `NetworkDescription` and
`DarknetWeightSource` as described in [API](API.md).

## Supported Darknet sections

| Section | Notes |
|---|---|
| `[net]` | `width`, `height`, `channels` |
| `[convolutional]` | `activation`; `batch_normalize`; `pad`, `padding`, `stride`, `size`, `filters`; `groups` = 1 only |
| `[maxpool]` | `size`, `stride`, `padding` (default `size - 1`, as Darknet) |
| `[upsample]` | `stride` (nearest-neighbour) |
| `[route]` | one or two inputs; negative indices are relative |
| `[shortcut]` | one `from` layer, added to the previous layer; `activation` |
| `[yolo]` | `mask`, `anchors`, `classes`, `scale_x_y` (Darknet box decoding) |

Activations for convolutions and shortcuts: `linear`, `leaky`, `relu` and `mish`.

Keys that do not change inference (learning rate, augmentation, ...) are ignored. Any other
section, activation or value that the library cannot run is rejected with an error that names
the section and line.

Requirements:

- The input size (`width`, `height`) should be a multiple of 32. The detector warns otherwise.
- The YOLOv3-tiny, YOLOv4-tiny, YOLOv3 and YOLOv4 section sets are supported. The shortcut
  arithmetic is tested with small networks; a published full-size `.cfg` has not been loaded
  yet.

## Tools

- `tinyyolo_make_weights model.cfg model.weights` (built by CMake) writes a `.weights` file
  that matches a `.cfg`. Its values are pseudo-random, for testing the pipeline.
- `tools/bin2header.py` turns files into `PROGMEM` byte arrays.

## Sample model

The Darknet examples `CameraDetect` and `DrawDetections` embed their model in `DarknetModel.h`
(generated by `tools/bin2header.py`). To make a test model, write a `.cfg`, run
`tinyyolo_make_weights model.cfg model.weights`, and convert the files with `tools/bin2header.py`.

## Memory

Weights are float32 by default, about 4 bytes per parameter. The sample model has 6,824
parameters and needs about 27 KB. With `WeightPrecision::Int8` the weights take about 7 KB
(see [Quantization](Quantization.md)).

Layer outputs share memory where their lifetimes do not overlap. On the mini test network,
this reduces activation memory from 23 KB to 15 KB.

Full YOLOv3-tiny has about 8.8 M parameters: about 35 MB as float32, or about 9 MB as int8.
That exceeds the RAM of most boards, so it needs PSRAM. On the ESP32 family every buffer is
requested from internal RAM first and placed in PSRAM when internal RAM cannot hold it (see
[Design](Design.md#model-memory)).

The model blob for flash (`tinyyolo_export_blob`) stores the int8 convolution weights in OHWI
order. Blobs exported before the OHWI change (int8 weights in OIHW) must be exported again.

## YOLO11 (Ultralytics)

YOLO11 is not a Darknet model, so it does not use the `.cfg`/`.weights` loader. It runs as a graph
of primitive operations (`src/TinyYolo/graph/Graph.h`) with an anchor-free head
(`src/TinyYolo/graph/AnchorFree.h`). Only the nano model (YOLO11n) has been tested.

### Get the model

`tools/yolo11/yolo11_fetch_models.sh` downloads the nano weights (checksum checked) into
`models/yolo11n/` and exports them (needs Python with `ultralytics`; set `PYTHON`):

```sh
PYTHON=python3 tools/yolo11/yolo11_fetch_models.sh
```

The model folder is described in `models/yolo11n/README.md`. The int8 scales are calibrated on one
image: the test photo by default, or `CALIBRATION_IMAGE` for another image.

### Examples and tools

| Name | Where | What |
|---|---|---|
| `yolo11_detect` | `desktop/yolo/yolo_detect.cpp` | desktop: detections on a PPM image, through `GraphYolo11` |
| `yolo11_check` | `desktop/yolo/yolo_check.cpp` | desktop: every layer against the PyTorch reference |
| `Yolo11Graph` | `examples/Yolo11Graph` | P4: the sample photo from flash, graph path |
| `Yolo11CameraStream` | `examples/Yolo11CameraStream` | P4: camera, streamed to `camera_view`, graph path |
| `yolo26_detect`, `yolo26_check` | `desktop/yolo/yolo_detect.cpp`, `desktop/yolo/yolo_check.cpp` | desktop: as the YOLO11 tools, for YOLO26n |
| `Yolo26Graph` | `examples/Yolo26Graph` | P4: the sample photo from flash; `kP4Kernels` selects the P4 kernels or ESP-NN |
| `Yolo26CameraStream` | `examples/Yolo26CameraStream` | P4: camera, streamed to `camera_view`, graph path |

The YOLO11 and YOLO26 tools and examples start with `yolo11`/`Yolo11` and `yolo26`/`Yolo26`; the YOLOv4
ones start with `yolov4`/`Yolov4` (`tools/yolov4_fetch_models.sh`, `examples/Yolov4CameraStream`). The
exporter (`tools/yolo/yolo_export.py`) and the table generator (`tools/yolo/yolo_gen_graph.py`) serve both
YOLO11 and YOLO26; the desktop tools are built per model by CMake (`yolo11_check`, `yolo26_check`, ...).

### YOLO26

`tools/yolo26/yolo26_fetch_models.sh` gets the YOLO26n checkpoint (checksum checked) and exports it like
YOLO11. YOLO26 differs from YOLO11 in three places, which the exporter and the decoder handle:

- No DFL: the box head predicts four distances directly (`reg_max` 1). `AnchorFreeLevel::reg_max`
  selects the decoding; the table's `kModel` carries it.
- The SPPF has a residual connection (`add`), exported as an `add` operation.
- One C3k2 block of the neck holds a Bottleneck followed by a PSA attention block, which uses the
  attention operation already in the graph.

The float graph matches the PyTorch reference (layer errors about 1e-4, head 3e-3) on the desktop,
and the sample photo gives class 17 (YOLO26n: score 0.891 float32, 0.881 int8 on the desktop).

### Export

```sh
python3 tools/yolo/yolo_export.py yolo11n.pt out/ photo.jpg   # needs the ultralytics package
```

The export writes, in `out/`:

| File | Content |
|---|---|
| `*_graph_weights.bin` | float32 parameters, batch norm folded (2616232 values) |
| `*_int8_weights.bin` | int8 convolution weights, OHWI (2606816 bytes) |
| `*_int8_scales.bin` | float32 weight scales, one per output channel (8136 values) |
| `*_graph.json` | the operation list |
| `*.inc` | the C++ tables: `kOps`, `kParams`, `kQuant`, `kQuantPerTensor`, `kDetectHeads`, ... |
| `ref_layer*.bin` | PyTorch reference outputs of the test photo |

`desktop/yolo/yolo_check.cpp` (target `yolo11_check`) runs the float graph on the desktop and compares every layer with the
reference (about 1e-4 for the nano model). `tools/yolo/yolo11n_graph.inc` is the table used by the
desktop checker. The checker's int8 mode uses the shared-scale table; add `--per-tensor` to use the
per-tensor one.

### Activation scales: two tables

The export emits two quantization tables. Pass one of them to `Graph::begin()`:

| Table | Scales | Speed | Accuracy |
|---|---|---|---|
| `kQuant` | shared scale per group of connected tensors (concat, add, chunk, max pool, upsample pass the int8 values through) | fast, the default | checked on the test photo |
| `kQuantPerTensor` | one scale per activation tensor | slower (requantization between operations) | more accurate |

The per-tensor table is the more accurate one. Its speed has not been measured on the current code.

### Weights on the board

On the ESP32-P4 the sketch reads one blob from the `model` partition (absolute offset 0x310000,
the same partition as the P4 examples; `examples/Yolo11Graph/partitions.csv`). The blob is the
three export files concatenated, in this order:

```
*_graph_weights.bin  +  *_int8_weights.bin  +  *_int8_scales.bin     (13104288 bytes)
```

Copy the int8 weights and scales into PSRAM at start-up (`MemoryPlacement::PsramFirst`); the flash
cache reads them slowly. The float parameters are read in place through the flash mapping.

### Running the graph

```cpp
#include <TinyYolo.h>
#include <TinyYolo/graph/AnchorFree.h>
#include <TinyYolo/graph/Graph.h>
#include <TinyYolo/backend/Esp32NnBackend.h>
#include "yolo11n_graph.inc"   // kOps, kParams, kQuant, kDetectHeads, ...

using namespace yolo11;

Graph graph;
Esp32NnBackend backend;   // int8 convolutions (P4 assembly kernels, ESP-NN otherwise)
Tensor input;
Detections candidates, detections;

// float parameters, int8 weights (PSRAM) and weight scales (PSRAM), from the blob above
graph.begin(kOps, kOpCount, kParams, kParamCount, weights, kTensorCount, kInputId,
            keep, keepCount, qweights, qscales, kQuant);
input.allocate(Shape(640, 640, 3));
candidates.reserve(2000);
detections.reserve(100);

// per frame: letterbox the image to 640x640 RGB, values in 0..1 (Preprocessor::letterbox)
graph.run(backend, input);

AnchorFreeLevel levels[3];
for (int l = 0; l < 3; ++l) {
  levels[l].box = &graph.tensor(kDetectHeads[l][0]);
  levels[l].cls = &graph.tensor(kDetectHeads[l][1]);
  levels[l].stride = kDetectStrides[l];
}
decodeAnchorFree(levels, 3, kDetectClasses, 0.25f, 0.7f, candidates, detections);
```

`keep` lists the tensors that must stay alive after their last use: the six detect-head tensors
(`kDetectHeads`). Everything else is freed after its last consumer. The detections are in
network-input pixels; map them back with the `LetterboxInfo` of the letterbox step.

Profiling: `graph.enableProfiling(true)` records the time per phase (`Graph::Phase`: quantize,
int8 convolution, dequantize, float convolution, grouped convolution, attention, other) and per
operation (`graph.opMicros(i)`).

### Performance

All variants are measured at the same 320x320 input on the same photo. The table with every
variant and board is in the [README](../README.md#performance).

The first convolution has 3 input channels. It is padded to 16 channels (zeros in channels 3 to 15,
and a zero border), so the aligned 16-channel kernel runs it. The kernel matches a naive integer
reference on every output of this layer shape.

The scores have been checked on one photo only.
